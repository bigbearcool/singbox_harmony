# Mate XTs / HarmonyOS 7 真机验收

## 2026-10-25 实测记录

- 设备：华为 Mate XTs，系统报告 `GRL-AL20`，HarmonyOS 7 / API 26，arm64-v8a。
- 使用本人生成的 DevEco 调试签名，包名 `com.bigbear.singbox`；已安装并确认系统 VPN 授权。
- 配置：内置直连诊断配置。没有使用用户代理节点或节点凭据。
- 基础网络：蜂窝 `rmnet0`，实际接口存在 IPv6 地址。Wi-Fi 场景未验证。
- 真实 TUN：`vpn-tun`，按 `172.19.0.1` 和 `fdfe:dcba:9876::1` 两个地址共同识别，未猜测接口名。
- 日志确认 `sing-box 1.14.3` 已加载，并在 VPN 进程中运行；公共 NetConn 出站 socket 绑定成功，所观测绑定失败计数为 0。

### 默认路由

VPN ConnectionProperties 返回 `0.0.0.0/0` 与 `::/0`，接口均为 `vpn-tun`。运行时另从 `/proc/net/ipv6_route` 观察到全零目的地址、前缀长度 `00` 的 `vpn-tun` 路由。

配置显式列出两条默认路由，接口与网关字符串为空，由服务填入真实接口。仅设置 `hasGateway:false` 而仍传入 `::` 网关，不能保证本设备路由落地；空路由列表的系统补全也不能代替显式 `::/0`。

### 数据面正向与负向

“检查连接”通过公共 API 把测试 socket 绑定到本应用实际 VPN NetID，排除本应用进程被豁免而直接通网的误判。

| 测试 | 直连诊断配置 | 加入 `::/0` 拒绝规则 |
| --- | --- | --- |
| IPv4 TCP HTTP HEAD → `223.5.5.5:80` | 成功，收到 HTTP 响应 | 成功 |
| IPv6 TCP HTTP HEAD → `[2400:3200::1]:80` | 成功，收到 HTTP 响应 | 未通过 |
| IPv4 UDP DNS A | 成功 | 成功 |
| IPv6 UDP DNS AAAA | 成功 | 成功 |

DNS 每个表格项包含两项查询：IPv4 为 `192.0.2.53` 与 `172.19.0.2`，IPv6 为 `2001:db8::53` 与 `fdfe:dcba:9876::2`。前者是保留文档地址，不运行真实上游 DNS；收到正确事务 ID、成功响应和答案，证明 53 端口被内核截获。后者覆盖系统配置的虚拟 DNS 地址。查询名为 `one.one.one.one`，A 通过 IPv4 UDP、AAAA 通过 IPv6 UDP 发出。此测试未覆盖 IPv6 非 DNS UDP 的远端转发。

负向配置是在直连配置的 `route.rules` 中加入 `{"ip_cidr":["::/0"],"action":"reject"}`。只有 IPv6 HTTP 失败，证明该测试流量进入内核路由。应用强制 DNS 截获规则位于该规则之前，因此负向配置中 DNS 仍成功是预期行为。

### 生命周期

连续 5 轮：连接 → UI 已连接 → 确认 `vpn-tun ::/0` → 断开 → UI 未连接 → 确认该默认路由移除，全部通过。没有据此声称 fd 泄漏或长期运行已经通过压力测试。

此段为 0.1 直连诊断基线。0.2 的实际用户配置与功能验证见下文；正常启动不保持窗口亮屏。

## 复现

1. 解锁手机并保持 USB 调试连接，安装签名 HAP。
2. `bash scripts/device.sh launch-test direct`，在 App 中连接并点击“检查连接”，确认四行成功。
3. 断开后 `bash scripts/device.sh launch-test reject-ipv6`，连接并检查，预期只有 IPv6 网页未通过。
4. 断开，使用 `launch-test direct` 恢复内置配置；完成后断开、`stop`、正常 `launch`。

诊断启动仅在 debug 构建生效，不覆盖真实用户配置；临时保持测试窗口亮屏。普通启动不保持亮屏。

## 0.2 实际配置与 SFM 功能验证

- 输入文件由用户提供，539427 字节，包含五个 VLESS 出站、一个用户态 WireGuard endpoint、urltest 与 selector 两组以及内联规则集。没有把密钥、节点地址或规则内容放入 Git。
- 添加 `with_wireguard` 构建能力，并只放行 `system:false`、无固定监听端口的 WireGuard endpoint。实际原文件通过同版本内核校验，签名更新后在手机读取与原文件逐字节一致。
- 配置库迁移、节点切换、恢复默认选择及远程配置测试后，原文件仍逐字节一致。当前选中的是用户配置。
- 实际配置已在蜂窝网络启动，观察到双栈 TUN 与默认路由，所观测出站绑定失败为 0。内核分组快照返回 2 组、3/6 个组成员，并已取得真实延迟结果；没有把延迟成功等同于所有节点和协议均已验收。
- 远程配置使用无凭据的 USB 回环 HTTP 测试服务：导入成功；返回无效配置时旧内容保持不变；返回有效更新时内容更新成功；切回原配置并确认删除测试配置成功。
- 实际内核的测速、切换、恢复选择、关闭全部连接、重连控制已取得对应请求 ID 的确认。原生测试另覆盖选择持久化、无效成员拒绝、日志清空和停止后实例释放。
- 重连测试发现旧版只调用 `CommandServer.Close()`，没有关闭运行实例；已补上 `CloseService()`。修复后在实际用户配置上重新执行 5 轮连接、IPv6 默认路由建立、断开、路由移除，全部通过。
- SSID 暂停/恢复、真实 Wi-Fi/蜂窝切换、后台存活、导出选择器和剪贴板首次授权尚未补充真机验收。功能与限制详见 [SFM 对应表](sfm-feature-matrix.md)。

HDC shell 曾拒绝 `/proc/net/if_inet6` 和执行 `/data/local/tmp` 程序；未把 native-smoke 标为通过。活动 VPN 的 `/proc/net/ipv6_route` 在本轮可读取，检查依据为签名 App 内自检与该路由观测。原始本机调试输出保存在被 Git 忽略的 `.deps/`，不包含节点凭据。

实际配置的首条 DNS 规则是对 AAAA 查询返回 `NOERROR` 空答案。客户端保留该策略，自检会分别确认 IPv6 HTTP 通网与 IPv6 UDP DNS 截获，并将后一项标为“已接管（配置返回空 AAAA）”；这不表示该配置会返回 IPv6 域名地址。没有擅自删除这条规则。

最终 0.2 签名包复测：IPv4/IPv6 HTTP 成功，IPv4 DNS A 成功，IPv6 UDP DNS 收到与原配置一致的空 AAAA 应答；节点选择与恢复已在界面上实际刷新。再次完成 5 轮路由建立/移除，结束时保留用户配置、VPN 已断开，调试亮屏、临时 HTTP 服务与 USB 端口转发均已关闭。

## 0.3 WireGuard 修复候选（2026-10-25）

用户反馈 0.2 家庭内网 IP 和域名均打不开。0.3 将 WireGuard 外层 UDP 改为受保护的客户端 socket 路径，同步检查 bind/Up 返回值，并显示白名单握手/计数信息。没有修改家庭服务端、peer、密钥或原始配置。

- 已签名安装 0.3.0，原始配置仍逐字节一致。蜂窝网络双栈 TUN 与 IPv6 默认路由确认，所观测 socket 绑定失败为 0。
- 实际 endpoint 使用 `protected-client-udp`，取得非零握手时间和加密 tx/rx。直接经该 endpoint 向原配置指定的家庭 DNS 发出有界查询，收到事务匹配的成功 DNS 应答（rcode 0）。此项证实加密通道至家庭 DNS 的往返；不代替其他 App 的业务服务验证。
- 绑定 VPN 网络的 IPv4/IPv6 HTTP 与 IPv4 DNS A 自检通过，IPv6 DNS 保留原配置的空 AAAA 策略。
- HDC shell 对家庭 resolver 数字 IP 的 ICMP 检查未收到响应；该 UID 路径及家庭 ICMP 策略未确定，不能据此断定业务路径失败或成功。
- 本机真实加密用户态 peer 测试覆盖外层 IPv4/IPv6/域名、内层 IPv4/IPv6和保护回调权限拒绝，Go race 通过。
- 用户在手机确认原先失败的家庭业务 IP 和域名均能打开。随后停止 App 确认旧 IPv6 默认路由移除，正常启动（无调试亮屏参数）并连接，确认新 IPv6 默认路由及家庭 DNS 成功应答。
- 测试结束保留原配置与已连接的 VPN，关闭调试亮屏。二维码扫码和系统 URI 分发仍待验收。

确切签名包已保存 `.deps/releases/0.3.0/entry-default-signed.hap`，SHA-256 及范围见 `build-verification.json`；0.2 历史记录见 `build-verification-v02.json`。
